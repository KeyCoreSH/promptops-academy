## **1\. Objetivo**

A Etapa 0 serve para organizar o projeto antes de começar a programação.

Nessa etapa, a equipe vai revisar como o sistema vai funcionar, como as informações serão organizadas, quem será responsável por cada parte e como as entregas serão avaliadas.

O desenvolvimento deve começar somente depois dessa validação.

---

## **2\. O que será validado**

Na Etapa 0, serão revisados:

* **Fluxo do sistema:** como o usuário vai encontrar, testar, melhorar e reutilizar os prompts.  
* **Wireframes:** organização das principais telas.  
* **Modelo de dados:** quais informações o sistema vai guardar.  
* **Backlog:** o que precisa ser feito.  
* **Responsabilidades:** quem ficará responsável por cada parte.  
* **Critérios de aceite:** como vamos saber se uma entrega está adequada.

---

## **3\. Minha função no projeto**

Como responsável por **Governança e Aceite**, minha função será acompanhar a qualidade dos resultados e ajudar a equipe a definir critérios para avaliar os prompts e os testes.

Minha parte envolve:

* criar a rubrica de qualidade;  
* definir regras para evitar informações inventadas;  
* acompanhar os status dos testes;  
* verificar questões de privacidade;  
* revisar resultados e evidências;  
* registrar riscos e decisões.

Essas são as responsabilidades previstas para a função de Governança e Aceite no projeto.

---

## **4\. Critérios de qualidade**

Os resultados serão avaliados principalmente por:

| Critério | O que será verificado |
| ----- | ----- |
| **Clareza** | O objetivo está fácil de entender? |
| **Consistência** | A resposta segue o contexto fornecido? |
| **Evidência** | Existe algo que comprove o resultado? |
| **Anti-invenção** | Foram evitadas informações não fornecidas? |
| **Privacidade** | Os dados usados no teste são adequados? |
| **Utilidade** | O resultado realmente ajuda na tarefa? |

---

## **5\. Regras importantes**

Durante os testes:

* não inventar números, métricas ou informações;  
* não apresentar suposições como fatos;  
* deixar informações faltantes claras;  
* não aprovar um teste que não foi realmente executado;  
* usar dados fictícios quando necessário;  
* não utilizar senhas, tokens ou informações confidenciais.

Essas regras seguem as orientações do projeto sobre anti-invenção, privacidade e avaliação dos resultados.

---

## **6\. Como será feita a avaliação**

Para cada teste, vamos registrar:

**O que foi testado → O que deveria acontecer → O que aconteceu → Qual é a evidência → Qual foi o resultado**

Os status serão:

* **Aprovado**  
* **Ajustar**  
* **Não aprovado**  
* **A executar**

Um teste só poderá ser considerado aprovado depois de ser executado e analisado.

---

## **7\. Melhoria dos prompts**

Quando um teste encontrar um problema, o prompt poderá ser alterado e testado novamente.

O processo será:

**v1 → teste → problema → ajuste → v2 → novo teste**

Assim, conseguimos mostrar se a mudança realmente trouxe uma melhoria. O projeto prevê esse acompanhamento por meio de versões, testes e ciclos de melhoria.
